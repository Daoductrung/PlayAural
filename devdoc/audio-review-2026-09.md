# Audio protocol v3 review, 19 September 2026

Review of commits 519896b, 13bacbc, 86c1b6d and db0ac1a by Rory Michie, against the real engine wherever one could be run. This file lists what was found and not fixed. What was fixed is on the `audio-review-fixes` branch and described in its commit messages.

Each item says how it was established: **measured** (run against the real server, wheel or test suite), **read** (follows directly from the code), or **plausible** (reasoned, needs a device or browser to confirm).

The design is sound. The axis mapping agrees across all four clients, renderer distance gain is neutral and applied once everywhere, generation-safe replacement is real, and the native mobile bridge is real code with correct handle lifetimes. The recurring weakness is that tests exercise fakes or match source text, so the numbers in the commit messages are true and prove little. Section 5 says what would have caught the bugs.

## 1. Web client

1. **Automation runs on animation frames, not the audio clock (read).** Source motion, gain automation, per-segment sequence motion and `fade()` each call `setValueAtTime` once per display frame (web_client/audio.js around lines 381, 444, 505, 1087). Browsers throttle or stop `requestAnimationFrame` for hidden tabs and fully covered windows, which is a normal state for a screen-reader user. While hidden, moving sources freeze, fades stall, and because `stopKey` awaits `fade()`, a stop with a fade never completes. Visible, the gain is a staircase at the display rate and can click on tonal material. These are closed-form curves with a known start: use `setValueAtTime` plus `linearRampToValueAtTime` for linear easing and `setValueCurveAtTime` with about 32 points for the quadratic easings, on `gain`, `positionX`, `positionY` and `positionZ`. Distance gain is not linear in position, so sample it into a curve as well. This removes all per-frame JavaScript, including the 32 callbacks per frame that a 32-segment moving chain runs today from the moment it is scheduled.
2. **The first HRTF sound of a session is probably silent on Chrome (plausible).** Chrome loads its HRTF database when the first HRTF panner is created and renders silence until it arrives. Create and discard one HRTF panner in `createAudioEngine`.
3. **An update that finishes before its asset loads is lost (read).** `applyMotionFrame` and its gain twin delete the record once elapsed passes the duration, even when no source exists yet, and `register()` only applies records still in the map. On a cold cache the source then sits at its original position and gain forever. Keep the final value per handle until the handle's generation changes.
4. **A non-looping seamless ambience loses its outro (read).** The loop node's `ended` handler calls `cleanup(key)`, which disconnects the outro that `scheduleStemOutro` just started.
5. **The tail analyser is more than the problem needs (read).** `cleanupAfterRenderedTail` puts an AnalyserNode on every HRTF effect and polls for silence for up to two seconds, to protect a tail of a few milliseconds. Meanwhile the finished source counts against `max_instances` and the 64 cap. A 50 ms timeout from `ended` does the same job.
6. **Capacity counts a sequence as one source (read).** It can hold 32 HRTF panners, so the worst case is 64 times 32 convolvers.
7. **Service worker (read).** `CACHE_NAME` was not bumped in 13bacbc or db0ac1a although audio.js changed, so an offline user keeps the older file. Module imports are unversioned, so a new audio.js can be paired with an old spatial_audio.js from the HTTP cache, and one missing export is a link error that takes down the whole app. Fetch the shell files with `cache: "no-cache"` or version the import URLs, and have layout_test.mjs fail when precached files change without a bump.
8. Older issues seen in passing: `unlock()` never resumes from iOS Safari's `interrupted` state and there is no `statechange` listener, so up to 32 stale queued effects fire together when the context returns; `refreshBus` calls `setValueAtTime` without `cancelScheduledValues`, so a duck change during a bus ramp jumps to the target; the cache handler stores every sound ever fetched without bound.

## 2. Mobile client

1. **Source creation decodes while holding the module's one lock (read).** `createSource` in PlayAuralSpatialAudioModule.kt and its Swift twin run the whole file decode, up to 32 files for a sequence, inside the lock that the synchronous `setParameters`, `drainEndedSources` and `destroySource` calls take on the JS thread. The 50 ms poll and every 60 Hz automation tick therefore stall for the length of the decode, on the thread that drives gestures and speech. Decode outside the lock and take it only to insert into the map.
2. **Per-segment gain and position switch on a JS timer (read).** Only the audio boundaries are scheduled natively. Gain, position, attenuation and blend for each segment are applied by a 16.7 ms `setInterval` working from an estimate of the native start time (MobileAudioManager.ts around line 2488), so the start of each segment plays with the previous segment's parameters for up to about 30 ms, longer when the JS thread is busy. The real fix is per-segment gain and position fields in `cosmos_mobile_source_config`, so the engine switches at the boundary; that is Cosmos work and can be requested.
3. **Pitch is set on the group, so pitched chains are not sample-accurate on mobile (plausible).** With pitch p on the group node, child sounds are read p times 512 frames per period and their start offsets are measured in those frames, which moves each boundary by up to (p - 1) times 512 frames. Set pitch on each segment's sound instead. Unpitched chains are unaffected.
4. **iOS has not been run (read).** No commit claims an iOS build or device test. Two things need a real Xcode build: whether `-lphonon` in the pod's `OTHER_LDFLAGS` reaches the final link, and whether expo-av keeps the AVAudioSession active when only native HRTF sources are playing, since the miniaudio device is configured not to activate it. If it does not, positioned sounds are silent or follow the ring switch.
5. **No audio focus handling for the native engine (read).** When a call or another app takes focus, expo-av players pause and the miniaudio stream keeps rendering.
6. Smaller: a failed native init disables HRTF until logout (nativeSpatialAudio.ts lines 192 and 202); `LongArray` returns are declared non-null but the C side returns NULL on allocation failure, which orphans a source; `System.loadLibrary` in an object initializer turns a load failure into `NoClassDefFoundError` on every later call rather than the clean fallback; the iOS fallback path has no left or right at all; the device and Steam Audio context never idle once started; modules/playaural-spatial-audio/src/PlayAuralSpatialAudioModule.ts and index.ts are never imported.
7. The Steam Audio verifier does fail closed on drift, but its expected hashes live in UPSTREAM.json beside the binaries, so it is a consistency check, not a tamper check. Pin the upstream archive hash in the script itself.
8. **Scheduled boundaries land on the period, not the frame, until the mobile module is rebuilt (measured).** Upstream miniaudio treats a node whose start time falls anywhere inside a graph read as stopped for that whole read, and one whose stop time falls inside a read as stopped for all of it, so a scheduled start is deferred to the next period boundary and a scheduled stop cuts from the previous one. An intro that stops and a loop that starts on the same transition frame therefore leave one full period of silence, 10.67 ms at 48 kHz, and every chain boundary is late by up to a period. Rendering the graph offline with no device (cosmos/miniaudio-sys/tests/scheduled_start.rs) shows a start at frame 100 arriving at 512, one at 700 at 1024, and a stop at 700 cutting at 512. The bundled miniaudio.h is patched on the branch and the same test shows every start and stop on its frame; the desktop wheel carries it, and Android compiles the same header, so the fix reaches mobile on its next native build. Item 3 stands regardless, since it is about which frames the offsets count.

## 3. Server, not fixed on the branch

1. **Nothing in production calls the v3 API (measured by search).** No game calls `move_*`, `set_*_gain`, `play_sound_chain`, `blend_ambience_layers`, `seat_of=`, `attenuation=` or a positioned play; 519896b removed the test menu that was the one caller. The first game to use it will be the first real test.
2. **Equal-power blending is equal-power only at rest (read).** `ambience_mix_gains` gives `sqrt(w)` endpoints, but the transition is a gain automation that interpolates amplitude, so a full crossfade passes through (0.5, 0.5): half power, a 3 dB dip at the midpoint, which is what equal-power exists to avoid. Interpolate the weight and take the square root at each step, as a new easing the clients evaluate.
3. **Automation keeps advancing while music is paused (measured).** `process_audio_automations` has no `state.paused` check. Whether that is a bug depends on whether clients freeze automation during a pause; the two must agree or a reconnecting listener hears a different position.
4. **Persisted seated loops keep their old seat angles when someone leaves (read),** while new one-shots from the same seat use the new geometry.
5. `_dispatch_seated_audio` skips the replayable-handle collision guard that `_dispatch_audio` applies; `AUDIO_PROTOCOL_VERSION` is never negotiated, so v3 packets go to every client; positioned chain segments get no fallback pan for non-spatial clients; `_audio_state_key(state.to_command(), ...)` builds and validates a whole command per state per operation when it needs six fields.

## 4. Desktop client, not fixed on the branch

These all wait on `is_playing` going false and start working once the Cosmos 0.3.1 wheel is built; check them then, in headphone mode with a positioned source: ambience intro to loop handoff (`wait_for_intro`), boundary outro (`wait_for_boundary`), release of ducking after a positioned one-shot, and the 64-effect cap.

1. **Ambience stems are stitched by polling, not scheduled (read).** 13bacbc says stems are scheduled on the engine timeline; on desktop the loop is started by polling `is_playing` every 5 ms, which with a 10.67 ms engine period leaves a gap of 5 to 25 ms. `schedule_at_engine_frame` and the duration arithmetic in `play_sequence` already exist; schedule the loop at the intro's start frame plus its duration.
2. **Automation that finishes during an intro is reverted at the loop handoff (read).** `install` rebuilds the loop source from the original position and gain, and only automations still running are reapplied.
3. **One thread per sound.** Every one-shot has a watcher thread polling at 20 Hz, every fade has a thread, every moving sequence segment has a thread polling at 60 Hz from scheduling time, and the intro and boundary waits poll at 200 Hz. One scheduler thread would replace them and reduce lock contention with the UI thread.
4. `play_sequence` decodes up to 32 assets on the wx thread and the Cosmos binding holds the GIL throughout, so an uncached chain stalls the UI and the screen reader. Releasing the GIL during load is Cosmos work and can be requested.
5. `_on_stream_end` always returns None, so `backend_callbacks` and every branch on it are dead; `normalize_spatial_mode` and its constants are defined in both sound_manager.py and sound_cacher.py; the automation helpers in spatial_audio.py revalidate an already frozen dataclass on every 60 Hz tick.

## 5. Tests

1. The conformance corpus has five attenuation vectors, all on the X axis, so an implementation that computes distance as `abs(x)` passes. None is inside the reference distance, none has a linear rolloff below 1, none makes `max_gain` bind. Motion and gain are sampled at 250 and 1000 ms only, so the second half of ease-in-out is checked only at its end, where every formula agrees. Add off-axis positions, a point inside the reference distance, an ease-in-out sample at 750 ms, a destination at the coordinate limit, and a direction vector that ties the web, mobile and desktop axis conventions together.
2. No test imports web_client/audio.js, because it needs `window`. An `OfflineAudioContext` render of impulse assets would make boundary contiguity and left or right placement checkable as numbers.
3. mobile-audio-lifecycle.test.mjs has 57 assertions that match source text and 6 that run code. The tests named for races (generation-guarded automation, bounded reservations, stale completion) check that strings exist, one of them that a call appears at least four times.
4. The desktop `FakeStream` reported a scheduled stream as playing, the opposite of Cosmos, which is how a chain that stopped after its first segment passed 243 tests. It is corrected on the branch. The general rule: every fake needs one test that runs the same assertions against the real thing, as client/tests/test_sound_manager_real_engine.py now does.
